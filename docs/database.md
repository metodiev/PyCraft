# Database

## Storage

Challenges live on disk as files and are **indexed** into the database at API
startup. That split is deliberate:

- Content is reviewable, diffable and greppable in pull requests.
- Relational integrity and cheap progress joins at runtime.
- The database is never the source of truth for content, so it can be rebuilt.

| Entity | Table | Purpose |
| --- | --- | --- |
| Learner | `users` | Identity, XP |
| Challenge | `challenges` | Indexed projection of on-disk content |
| Submission | `submissions` | Every Run and Submit, with results and metrics |
| Challenge progress | `challenge_progress` | Per-user, per-challenge state and best score |
| Skill progress | `skill_progress` | Accumulated mastery per skill node |
| Tutorial reading | `tutorial_reads` | Per-user, per-tutorial read marker (grants no XP) |

## Development

SQLite is the default — no setup:

```
sqlite+aiosqlite:///backend/.pycraft.db
```

The schema is created automatically at startup. Delete the file to start over.

## PostgreSQL

```bash
export PYCRAFT_DATABASE_URL="postgresql+asyncpg://pycraft:pycraft@localhost:5433/pycraft"
```

Use `docker compose up postgres` for a local instance; it publishes on **5433**
so it does not collide with a PostgreSQL already running on the machine. When
not SQLite, the engine uses a connection pool with `pool_pre_ping`.

## Migrations

The schema is managed by **Alembic**. `alembic/` holds the environment and the
revision history; there is one baseline revision describing the whole schema.

```bash
cd backend
.venv/bin/alembic upgrade head          # apply everything pending
.venv/bin/alembic current               # what revision is applied
.venv/bin/alembic history               # the revision list
.venv/bin/alembic downgrade -1          # step back one revision
```

The database URL is **not** in `alembic.ini`. `alembic/env.py` reads it from the
application's `Settings` (`PYCRAFT_DATABASE_URL`), so a migration always runs
against the same database the app uses — keeping the URL in two places is
exactly how they drift apart.

### At application startup

`prepare_schema` runs during startup and handles three cases, because they are
genuinely different:

| Situation | Action |
| --- | --- |
| Fresh database | `upgrade head` builds the schema |
| Predates migrations (tables exist, no `alembic_version`) | **stamped** to the baseline, so later migrations apply cleanly |
| Already under migration control | `upgrade head`, a no-op when current |

The middle case is what lets an existing installation upgrade in place. It is
stamped only when the live columns **provably match** the models; a database
altered by hand is reported and left alone, because stamping it would record a
revision it does not actually match.

Set `PYCRAFT_AUTO_MIGRATE=false` when migrations belong to a release step rather
than the app. Startup then only *checks* the schema and logs drift, instead of
changing it behind a deployment's back:

```bash
cd backend && .venv/bin/alembic upgrade head
PYCRAFT_AUTO_MIGRATE=false .venv/bin/uvicorn app.main:app
```

### Writing a migration

```bash
cd backend
.venv/bin/alembic revision --autogenerate -m "add x to y"
```

Review the generated file before committing — autogenerate is a good first
draft, not an authority. `compare_type` and `compare_server_default` are on, so
a widened column or a changed default is detected rather than silently ignored.
`render_as_batch` is enabled because SQLite cannot alter most things in place;
batch mode rewrites the table, so one migration serves both SQLite and
PostgreSQL.

Model metadata uses an explicit naming convention (`NAMING_CONVENTION` in
[`app/db/base.py`](../backend/app/db/base.py)), so autogenerated constraint names
are deterministic and stable across databases.

To check a migration is complete, run `upgrade head` against a **fresh**
database and then autogenerate again: an empty revision means the migration and
the models agree. `tests/test_migrations.py` asserts this, along with the round
trip — `upgrade` followed by `downgrade base` leaves no tables behind.

## Content indexing

At startup:

1. `ChallengeRepository.load_all()` walks `challenges/*/*/metadata.json`.
2. Each challenge is validated (id/track/directory agreement, required files,
   at least one visible and one hidden test).
3. Valid challenges are upserted into `challenges` by primary key.
4. Invalid ones are logged (`Challenge content problem: …`) and skipped; the API
   keeps serving everything else.

A challenge removed from disk is **not** deleted from the database, because
submissions reference it. Prune deliberately if you need to:

```sql
DELETE FROM challenges WHERE id = 'obsolete-challenge-id';
```

Foreign keys cascade to `submissions`, `challenge_progress` and
`skill_progress`, so this removes learner history for that challenge too.

Tutorials are indexed the same way but are **not** projected into the database —
they are read-only content, so the in-memory catalogue is the whole story. That
is why `tutorial_reads.tutorial_id` is a plain string rather than a foreign key:
there is no row for it to reference. A read marker whose tutorial has since been
removed from disk simply never appears in a response, because the API builds the
catalogue from the on-disk content and only annotates it with read state.

## Progress semantics

- A `challenge_progress` row is created on first Run or Submit.
- `attempts` increments on every execution.
- `best_score` tracks the highest Submit score, updated **after** grading.
- Completion requires `score >= 60` **and** zero failed tests, and is recorded
  once — re-passing does not award XP again.
- XP accrues to `users.xp`; skill mastery and XP are updated per skill listed in
  the challenge metadata.
